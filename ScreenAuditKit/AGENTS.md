# ScreenAuditKit — Agent & Contributor Guidelines

This file governs how AI agents and human contributors work inside the **ScreenAuditKit** package.
Follow every section. These are not suggestions.

When this package lives inside a monorepo the root `AGENTS.md` also applies and takes precedence
on any cross-cutting concern (simulator management, system safety, git policy, etc.).
When the package lives in its own standalone repository, **this file is the sole authority**.

---

## What This Package Is

ScreenAuditKit is a deterministic screenshot validation engine shipped as a Swift Package with:
- A **library** (`ScreenAuditKit`) — contract decoding, evidence extraction, rules, visual inspectors, reports
- A **CLI executable** (`screenaudit`) — fastlane and CI/CD integration entry point

It must remain **generic**: no RA11y app imports, no hardcoded project paths, no app-specific logic
in `Sources/`. App-specific contracts and adapter scripts live in the consuming project.

---

## System Safety — Prohibited Commands

Never run the following without explicit written approval from the user in the current conversation:
- Any `sudo` or `su` command
- `killall` or `kill` targeting any system daemon
- `xcrun simctl erase`, `delete`, or `shutdown all`
- `rm -rf` on any directory outside `.build/` or `build_results/`
- Any command that modifies macOS system state, Xcode toolchain, or developer certificate stores
- `git push --force` on any branch

---

## File System Boundary

Work only inside the `ScreenAuditKit/` package directory (or its path when in a standalone repo).
Do not read or write files outside the package root unless explicitly directed by the user.

Permitted output locations:
- `.build/` — SwiftPM artifacts (gitignored)
- `Docs/FeatureWalkthrough/Artifacts/` — curated walkthrough output (committed, generated by CLI)
- `Docs/FeatureWalkthrough/images/` — flattened image copies for Markdown (committed, generated by CLI)

---

## Build and Test Workflow

Always use these commands. Do not invoke Xcode, `xcodebuild`, or anything outside SwiftPM.

```bash
# From the package root (directory containing Package.swift)
swift build                    # Build library + CLI
swift test                     # Run full test suite (75+ tests)
swift run screenaudit --help   # Verify CLI is wired
```

Do not use `utility/build_and_test.sh` — that script is RA11y monorepo specific.
Do not use `swift test --filter` to skip tests without explicit user instruction.

**Before opening a PR:** `swift build` and `swift test` must both pass with zero errors and
zero warnings on the current Swift/macOS toolchain.

---

## Package Architecture — Six Layers

Maintain the layered design. Do not collapse layers or introduce cross-layer shortcuts.

| Layer | Directory | Responsibility |
|-------|-----------|---------------|
| Contracts | `Sources/ScreenAuditKit/Contracts/` | JSON contract decoding and validation |
| Evidence | `Sources/ScreenAuditKit/Evidence/` | PNG metadata extraction, injectable OCR |
| Rules | `Sources/ScreenAuditKit/Rules/` | Contract-vs-evidence deterministic evaluation |
| Validation | `Sources/ScreenAuditKit/Validation/` | End-to-end orchestration |
| Reports | `Sources/ScreenAuditKit/Reports/` | JSON, Markdown, overlay PNG output |
| Visual | `Sources/ScreenAuditKit/Visual/` | Pluggable pixel-level inspectors |

Each layer is independently testable. Visual inspectors must not depend on Contracts.
Rules must not depend on Reports. The CLI (`Sources/screenaudit/`) depends only on the library.

**New feature checklist:**
1. New rule → new `ScreenAuditRuleID` case + test in `ScreenAuditRuleTests.swift`
2. New inspector → new file in `Visual/` + test file + fixture PNG
3. New contract field → version `schemaVersion` + migration note in `ScreenAuditContracts.swift`
4. New CLI flag → new argument parser in `ScreenAuditKit.swift` + test in `ScreenAuditCLITests.swift`

## Generic-First Rule

The `Sources/ScreenAuditKit/` library target must contain **zero** references to:
- RA11y, quest names, game mechanics, or pedagogy
- Hardcoded file paths that include a consuming project's directory structure
- Any bundled contract files — contracts are caller-supplied data, not library data

If you find RA11y-specific logic in `Sources/`, extract it to the consuming project.
The `Docs/` and `Tests/` directories may include RA11y-style examples as illustrative fixtures —
clearly label them as examples, not required conventions.

---

## Access Control

Default to the **most restrictive** access that still permits the intended use:

- `private` — single file, single type
- `internal` — within the module (default; use for implementation details)
- `public` — required across module boundary (library → CLI, or library → consumer)

Do not make types or functions `public` solely because they "might be useful to consumers someday."
Public API is a contract. Every public symbol must have a doc comment.

The `ScreenAuditFeatureWalkthroughArtifactExporter` is `public` because the CLI target imports
it — but its implementation details (`pathPlaceholder`, helper methods) are `private`.

---

## Concurrency

This package targets Swift 6 strict concurrency. Every new type must satisfy:
- `Sendable` conformance (or `@unchecked Sendable` with an explicit comment explaining why)
- No `@MainActor` on pure data types or validators
- Structured concurrency only — no `Task.detached` without documented justification
- No global mutable state

---

## Contract Schema Versioning

The JSON contract schema is versioned via `schemaVersion`. Any breaking field change must:
1. Increment `ScreenAuditContracts.supportedSchemaVersion`
2. Return `ScreenAuditContractError.unsupportedSchemaVersion` for old schemas
3. Add a fixture file in `Tests/ScreenAuditKitTests/Fixtures/` covering the old version

Do not silently ignore unknown JSON keys — unknown keys are decoded and ignored by default;
this is intentional for forward-compatibility.

---

## CLI Commands

Current commands. Do not add commands without a corresponding test in `ScreenAuditCLITests.swift`:

```
screenaudit --help
screenaudit --version
screenaudit validate --screenshots <dir> --contracts <file> --output <dir> [--baselines <dir>] [--ocr none|vision]
screenaudit export-feature-walkthrough [--package-root <dir>]
```

Exit codes are stable API — never change exit code values:
- `0` Success
- `1` Validation failed (hard findings)
- `2` Usage/config error
- `3` Input error (bad file, schema mismatch)
- `4` Runtime error

## Feature Walkthrough Export

The `export-feature-walkthrough` command curates test artifacts into `Docs/FeatureWalkthrough/`.

**Workflow:**
```bash
swift test                                    # generates .build/test-artifacts/feature-walkthrough/
swift run screenaudit export-feature-walkthrough --package-root .
# or via the wrapper:
bash Utility/export_feature_walkthrough.sh
```

The exporter sanitizes absolute machine paths before committing artifacts — do not bypass this.
Do not manually copy files from `.build/` into `Docs/` — always go through the exporter.

---

## Testing Conventions

- Every new public type needs at least one test file
- Fixture PNGs are synthesized in tests (AppKit drawing) — do not commit real app screenshots as fixtures
- Use `@testable import ScreenAuditKit` in `ScreenAuditKitTests`; `ScreenAuditCLITests` tests the public CLI surface only
- Do not add XCTest dependencies on network, simulator, or Xcode Cloud — tests must run fully offline with `swift test`
- The `Fixtures/` directory in the test bundle holds JSON contract fixtures; PNG fixtures are synthesized at test time

---

## Before Committing

1. `swift build` — zero errors, zero warnings
2. `swift test` — all tests pass
3. No RA11y-specific strings in `Sources/ScreenAuditKit/`
4. No hardcoded absolute paths in any committed file
5. New public symbols have doc comments
6. `Tasks.md` updated if a milestone is completed or a new task is discovered
7. `CHANGELOG.md` entry if this changes public API or CLI flags (once the package has a changelog)
