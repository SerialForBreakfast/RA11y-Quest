RA11y - MVP Ticket Breakdown
Date: 2026-02-20

Notes
=====
- Derived from Phase 2 milestones. Each ticket: User Story, Requirements, Acceptance Criteria, Unit Test.
- Tickets are organized into tracks and dependency-ordered within each track.
- Tracks can be worked in parallel where noted.
- Design track lives in memlog/requirements/Design/ (separate files); this document references timing only.
- NEW = added during review. FIXED = corrected from original.

Status Values
=============
- Done       — Implemented, tested, and merged. All acceptance criteria verified.
- In Progress — Actively being worked. Only one ticket should be In Progress at a time.
- Ready      — All dependencies met. Can be picked up immediately.
- Blocked    — Waiting on one or more incomplete dependencies (listed in each ticket).

Tracks
======
- Infrastructure (M0, M1)      — Foundation; unblock all other tracks.
- UX / Gating (M2, M3, M4)    — User flows; depends on Infrastructure.
- Games (M5, M6, M7)           — Game implementations; depends on Infrastructure + UX/Gating. (S1 spike closed)
- Polish (M8)                  — Stability + audit; depends on all Games.
- Design (Parallel)            — Asset work; starts M1, must land before M5.

TICKET-M0-DesignTokens [NEW]
===============================
Ticket: M0 - Shared Design Token System
Status: Done

User Story
----------
As a developer
I want a single source for typography, spacing, and color constants
So that all screens are visually consistent and can adopt system accessibility overrides correctly.

Requirements
------------
- Define design tokens covering:
  - Typography: font styles aligned to Dynamic Type text styles (title, headline, body, caption).
  - Spacing: a small step scale (e.g., 4, 8, 12, 16, 24, 32pt).
  - Corner radius: consistent values (e.g., card, button, badge).
  - Colors: semantic color set (background, surface, primary, secondary, destructive) using adaptive
    Color assets compatible with Increase Contrast and Dark Mode.
- Tokens must be defined in a way that resolves correctly under system accessibility overrides
  (Increase Contrast, Reduce Transparency, Dark Mode).
- No raw numeric literals for spacing, radius, or color in UI code; token references only.

Acceptance Criteria
-------------------
- Token definitions exist and are consumable from SwiftUI views.
- Changing a token propagates correctly to all uses.
- UI remains legible under Increase Contrast and Dark Mode.

Useful Unit Test
----------------
- Color token for primary surface returns a non-zero opacity value in both Light and Dark
  trait environments (validates token is configured, not inadvertently transparent).

Dependencies
------------
- None

I want results shown as a simple rank with supporting metrics

TICKET-M1-GameSessionLifecycle [NEW]
===============================
Ticket: M1 - Game Session Lifecycle / State Machine
Status: Done

User Story
----------
As a developer
I want a shared, testable game session state machine
So that all games handle start, pause, stop, abandon, and completion consistently
and scoring is never written in an invalid state.

Requirements
------------
- Define a GameSession state machine with states:
  - idle, running, paused, completed, abandoned
- Transitions:
  - idle -> running (start)
  - running -> paused (app backgrounded or full-screen exited)
  - paused -> running (returned to full-screen)
  - running -> completed (success condition met)
  - running -> abandoned (timeout, or VO turned off mid-game; see M2-VOStateChangeMidGame)
  - paused -> abandoned (session invalidated while paused)
- Only completed state is eligible to write a best result.
- Session tracks: startTime, elapsed time (accounts for pauses), mistake count.
- Session must be injectable / testable (no direct UIApplication or timer dependencies in the model).

Acceptance Criteria
-------------------
- Starting a session and recording a mistake increments the count correctly.
- Pausing and resuming preserves elapsed time correctly.
- Reaching abandoned state does not trigger a storage write.
- Reaching completed state with a valid result triggers a storage write.

Useful Unit Test
----------------
- Given a session that is paused then abandoned, the resulting state is abandoned
  and no result is passed to storage.
- Given a session that completes, the result passed to storage matches the session's
  elapsed time and mistake count.

Dependencies
------------
- M1 Scoring Model, M1 StorageComponent

TICKET-M2-VOStateChangeMidGame [COMPLETE]
===============================
Ticket: M2 - VoiceOver Disabled Mid-Gameplay
Status: Done

User Story
----------
As a user
I want the game to handle VoiceOver being turned off during play gracefully
So that the app doesn't end up in an inconsistent or unscored state.

Requirements
------------
- Subscribe to VoiceOver state change notifications during an active game session.
- If VoiceOver transitions OFF while a game session is running or paused:
  - Transition game session to abandoned state.
  - Do not write a result (abandoned sessions are not scored; see GameSessionLifecycle).
  - Navigate to the VO Off interstitial, not to the result screen.
- If VO is re-enabled, user must restart the game; no resume from mid-session.

Acceptance Criteria
-------------------
- With a game running and VO toggled off, the session ends in abandoned state.
- No result is written to storage.
- User lands on the interstitial, not the result screen.

Useful Unit Test
----------------
- Given an active GameSession, injecting a voiceOverDidDisable event causes
  the session to transition to abandoned and calls the abandon handler, not the
  completion handler.

Dependencies
------------
- M2 VoiceOverStateProvider, M1 GameSessionLifecycle

TICKET-M3-Hub-UI-Progress [FIXED]
===============================
Ticket: M3 - Hub UI + Quest Board
Status: Done

User Story
----------
As a user
I want a hub that feels like a D&D quest board and shows my progress per game
So that I can choose a trial, see my best rank, and feel like I'm inside a game — not a tutorial app.

Visual Theme — The Tavern Quest Board
--------------------------------------
The hub is a tavern quest board. Three quests are pinned to it, each on an aged parchment
quest card. The environment is a warm, torchlit stone interior. The Dungeon Master's
voice greets the player at the top.

This is the player's home base. It should feel atmospheric and inviting, not clinical.
Reference the existing background art style: warm amber torchlight, stone arches,
dark but not oppressive. See simon_room_bg.png for the established palette and feel.

Screen Structure
----------------
Navigation bar
  - Title: "RA11y" (small, system font)
  - No back button at hub level

DM Greeting Header (below nav bar)
  - Text: "Choose Your Trial, Adventurer"
  - Style: slightly stylized heading; parchment-toned text on a dark stone band
  - Not interactive; purely atmospheric

Scrollable Quest Card List (3 cards, one per game)
  - See Quest Card spec below
  - Cards scroll vertically; no horizontal scroll
  - Sufficient spacing between cards to prevent accidental activation

Footer Area (always visible, does not scroll away)
  - "VoiceOver Basics" scroll button (secondary, parchment-style)
  - Conditional: "Enable VoiceOver" help affordance (see below)

Quest Card Spec (one per game)
--------------------------------
Each card represents one game. Tapping anywhere on the card starts the game
(after VoiceOver gating check — M2). Cards must be large enough for comfortable
VoiceOver focus (minimum 44pt height; recommended ~120pt).

Content per card:
  - Thumbnail: square illustration, rounded corners, 72x72pt
    (use game-specific asset when available; placeholder until Design track delivers)
  - Game title (large, bold): e.g., "The Enchanter's Trial"
  - One-line goal (secondary text): e.g., "Navigate focus and invoke the named relic"
  - Estimated duration: e.g., "~5 min"
  - Rank badge (trailing side):
    - D&D rank display names: Legendary / Skilled / Novice / Defeated / Quest Awaits
    - "Quest Awaits" when no result exists (not "Not played")
    - Badge MUST convey rank by BOTH shape and color (wax seal shape per rank, not color alone):
        Legendary → 6-pointed star seal
        Skilled   → shield seal
        Novice    → circle seal
        Defeated  → broken shield seal
        Quest Awaits → open scroll seal (no color fill)
    - Badge shows rank text label below the shape (text is primary; shape is reinforcement)

Card visual treatment:
  - Background: dark warm-toned card surface (dark brown/charcoal, NOT flat gray)
  - Border: subtle amber/gold accent border
  - Slight elevation shadow to lift card off background
  - Thumbnail area: slightly inset panel

State variations:
  - Unplayed: thumbnail is slightly desaturated; rank area shows "Quest Awaits" scroll
  - Played: thumbnail at full saturation; wax seal with rank color
  - Best rank improved (just returned from game): brief accessible announcement only —
    no animation unless Reduce Motion is OFF

VoiceOver Help Affordance (conditional — VO OFF only)
------------------------------------------------------
- Shown only when VoiceOver is disabled (from HubViewModel.showHelpAffordance)
- Pinned at the bottom of the screen, above the safe area
- Visual: torch/lantern icon + "Enable VoiceOver to play"
- Tapping opens the VO interstitial (M2)
- Must NOT be present in the view hierarchy when VO is ON (not focusable, not hidden)

VoiceOver Basics Button (always visible)
-----------------------------------------
- Always accessible regardless of VO state or first-run status
- Visual: parchment scroll style, secondary prominence
- Label: "VoiceOver Basics"
- Navigates to the first-run basics sequence (M4 entry point)

Accessibility
-------------
Reading order (linear, top to bottom):
  1. "RA11y" (navigation title)
  2. "Choose Your Trial, Adventurer" (heading role)
  3. Quest card 1 — combined label: "{title}. {goal}. {duration}. Rank: {rank}."
     accessibilityHint: "Double-tap to begin this trial."
  4. Quest card 2 — same pattern
  5. Quest card 3 — same pattern
  6. "VoiceOver Basics" button
  7. "Enable VoiceOver to play" button (only if VO OFF)

Rank badge: accessibilityLabel on the badge itself is empty (decorative);
  rank is part of the card's combined accessibility label.
"Quest Awaits" accessibility label: "Quest Awaits. Not yet attempted."

Dynamic Type: all text uses ra11y* font tokens; layout reflows at large sizes.
Increase Contrast: card borders and text meet WCAG AA contrast against the dark card background.
Reduce Motion: no ambient animations (torch flicker, sparkle) when Reduce Motion is ON.
Tap target: entire card is one interactive element, minimum 44x44pt.

Component Architecture
-----------------------
Portrait-locked. Single adaptive layout covers all iPhone and iPad sizes.

View files (RA11y-iOS/Hub/):
  iOSHubView.swift              Root; owns HubViewModel; uses .background{} modifier (not ZStack peer)
  iOSHubBackgroundView.swift    Full-bleed bg; fallback color + image + gradient; ignoresSafeArea; no game data
  iOSHubDMGreetingView.swift    "Choose Your Trial, Adventurer"; .isHeader; non-interactive
  iOSQuestCardView.swift        Button wrapper; combined a11y label; HStack/VStack per dynamicTypeSize
  iOSQuestCardInfoView.swift    Title / goal / duration text; .layoutPriority(1)
  iOSQuestThumbnailView.swift   Asset image + SF Symbol placeholder; @ScaledMetric size, capped
  iOSRankBadgeView.swift        SwiftUI Canvas shape (no PNG) + rank label; fixed width ~60pt
  iOSHubFooterView.swift        safeAreaInset .bottom container; basics button + conditional affordance

Layer model (.background {} modifier pattern):
  Background: iOSHubBackgroundView — fallback Color + Image(.fill, .clipped) + LinearGradient
    Applied via .background { } on the content ScrollView, NOT as a ZStack peer.
    Reason: ZStack peer approach causes landscape image intrinsic width (~1500pt) to inflate
    the ZStack's reported width, breaking the content layout. .background{} isolates sizing.
    Gradient: LinearGradient(colors: [.black.opacity(0.55), .black.opacity(0.25)], top→bottom)
    Ensures WCAG AA contrast for text against any image lighting condition.
  Foreground: ScrollView (VStack: DM greeting | quest card list | safeAreaInset footer)

Quest card internal layout — HStack(alignment: .top, spacing: 12):
  Left:   iOSQuestThumbnailView — fixed frame; capped @ScaledMetric; not DT-driven
  Center: iOSQuestCardInfoView  — .layoutPriority(1); wraps text naturally; grows card height
  Right:  iOSRankBadgeView      — fixed ~60pt wide; Canvas shape + .caption label (may wrap 2 lines)

Dynamic Type:
  Standard layout: HStack (thumbnail | info | badge)
  At dynamicTypeSize >= .accessibility2 → VStack layout:
    Top row: thumbnail (leading) + badge (trailing) in HStack
    Below:   iOSQuestCardInfoView full width
  Thumbnail: @ScaledMetric(relativeTo: .body) starting 72pt; capped 96pt iPhone / 108pt iPad
  Rank badge Canvas shape: always 48x48pt; label (.caption) allowed to wrap

iPhone vs iPad (portrait locked):
  Metric                  iPhone (.compact)      iPad (.regular)
  Content max width       screen − 32pt          600pt centered (.frame(maxWidth: 600))
  Card horizontal padding 16pt                   24pt
  Card spacing            16pt                   20pt
  Thumbnail cap           96pt                   108pt

Footer pinning:
  .safeAreaInset(edge: .bottom) on ScrollView — NOT an overlay.
  Automatically insets scroll content by footer height; last card never occluded.

Asset vs SwiftUI-drawn:
  Background images   → .xcassets (supports Dark Mode variants)
  Game thumbnails     → .xcassets with SF Symbol placeholder until Design track delivers
  Rank badge shapes   → SwiftUI Canvas / Path — geometric, no PNG, perfect at any point size
  Footer icons        → SF Symbols — automatic weight + DT scaling

Accessibility containment:
  Each iOSQuestCardView Button is a single VoiceOver focus element.
  All sub-views (thumbnail, info, badge) carry .accessibilityHidden(true).
  Button label: "{title}. {goal}. {duration}. Rank: {rankLabel}."
  Button hint: "Double-tap to begin this trial."
  DM greeting: .accessibilityAddTraits(.isHeader)
  VO help affordance: removed from view hierarchy when VO is ON (not just hidden).

Annotated component diagram: memlog/requirements/Design/Mockups-v2/mock_v3_hub_component_diagram.png

Requirements
------------
- Render 3 MVP games from GameDefinition catalog using the Quest Card spec above.
- DM greeting header is non-interactive and read as a heading by VoiceOver.
- Each card combines title + goal + duration + rank into a single accessibility label.
- Rank badge uses SwiftUI Canvas shape AND text label (no PNG, no color-only differentiation).
- "Quest Awaits" state for unplayed games (not "Not played").
- VoiceOver help affordance: absent from view hierarchy (not hidden) when VO is ON.
- VoiceOver Basics button: always present.
- After a game completes, hub rank updates without relaunch.
- Reduce Motion respected: no ambient animations when enabled.
- Dynamic Type layout switch at .accessibility2+: card switches to VStack arrangement.
- iPad: content max 600pt centered; iPhone: full width minus 32pt padding.
- Dark gradient overlay ensures contrast at all Dynamic Type sizes.

Acceptance Criteria
-------------------
- Hub renders all 3 games from catalog with correct titles, goals, and durations.
- After a game completes, hub reflects updated best rank without requiring relaunch.
- Rank badge displays both a Canvas-drawn shape and a text label.
- With VO OFF: help affordance is present and tappable.
- With VO ON: help affordance is absent from view hierarchy entirely.
- "VoiceOver Basics" is always accessible.
- With Reduce Motion ON: no ambient animations render.
- Reading order is correct and linear in VoiceOver.
- At dynamicTypeSize .accessibility2+: card uses VStack layout with no truncation.
- On iPad (768pt+ canvas): content is max 600pt and centered.
- Last quest card is not occluded by footer at any Dynamic Type size or device.

Useful Unit Test
----------------
- Given stored results for two games (one Legendary, one Novice), hub view model returns:
  "Legendary" and "Novice" for those games and "Quest Awaits" for the third.
- Given VO ON, HubViewModel.showHelpAffordance is false.
- Given VO OFF, HubViewModel.showHelpAffordance is true.

Dependencies
------------
- M0, M1 (Catalog, Storage, Scoring Model), M2 (VoiceOverStateProvider, HelpAffordance)

Theme / Narrative

TICKET-S1-Spike-ScrollObservability [CLOSED — RESOLVED BY ANALYSIS]
===============================
Ticket: S1 - Spike: Scroll Observability in SwiftUI
Status: Done

Resolution (2026-02-20)
-----------------------
Closed without prototype. All three spike unknowns are resolved by analysis:

1. API stability:
   `onScrollGeometryChange(for:of:action:)` + `ScrollGeometry` are iOS 18+ native
   APIs (stable, documented). Our minimum deployment is iOS 18. No fallback needed.
   `ScrollGeometry` exposes `visibleRect`, `contentOffset`, `contentSize`, `bounds`.

2. Update frequency:
   Using `Bool` as the equatable transform output means the action closure fires
   at most once — when the target first enters the visible rect. No update spam.

3. Recommended strategy:
   Strategy B from Spike-ScrollObservability-SwiftUI.txt ("target visibility boolean")
   is confirmed correct. Canonical implementation pattern for M7:

     .onScrollGeometryChange(for: Bool.self) { geometry in
         geometry.visibleRect.intersects(targetFrame)
     } action: { _, isReachable in
         if isReachable { targetIsReachable = true }
     }

   The pure function `targetIsReachable(visibleRect:targetFrame:) -> Bool` is
   unit-testable without device (injected geometry values).

One Remaining Question (folded into M7)
----------------------------------------
Does `onScrollGeometryChange` fire correctly when VoiceOver performs a 3-finger
scroll? Since the modifier observes scroll geometry (the outcome, not the gesture),
the answer is almost certainly yes — but this must be confirmed on device at the
start of M7 implementation before proceeding with the full level build.
Add this as the first M7 acceptance criterion.

Spike gate is lifted. M7 may open once M0/M1/M2 and Design track are complete.

Original User Story
-------------------
As a developer
I want a proven approach to observe scroll progress in SwiftUI
So that Scroll Hunt (M7) can be implemented reliably on iOS 18/26.

------------
