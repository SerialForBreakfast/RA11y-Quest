User Story
----------
As a user
I want the app to launch into a stable, navigable shell
So that I can reach the hub and return from any screen without dead ends.

- Provide an app entry route that leads to the Hub.

- Navigation can push to a placeholder "Game" route and return to the Hub.
- No screen has unreachable controls when VoiceOver is enabled.

TICKET-M0-DesignTokens [NEW]
===============================
Ticket: M0 - Shared Design Token System

User Story
----------
As a developer
I want a single source for typography, spacing, and color constants
So that all screens are visually consistent and can adopt system accessibility overrides correctly.

Requirements
------------
- Define design tokens covering:
  - Typography: font styles aligned to Dynamic Type text styles (title, headline, body, caption).
  - Spacing: a small step scale (e.g., 4, 8, 12, 16, 24, 32pt).
  - Corner radius: consistent values (e.g., card, button, badge).
  - Colors: semantic color set (background, surface, primary, secondary, destructive) using adaptive
    Color assets compatible with Increase Contrast and Dark Mode.
- Tokens must be defined in a way that resolves correctly under system accessibility overrides
  (Increase Contrast, Reduce Transparency, Dark Mode).
- No raw numeric literals for spacing, radius, or color in UI code; token references only.

Acceptance Criteria
-------------------
- Token definitions exist and are consumable from SwiftUI views.
- Changing a token propagates correctly to all uses.
- UI remains legible under Increase Contrast and Dark Mode.

Useful Unit Test
----------------
- Color token for primary surface returns a non-zero opacity value in both Light and Dark
  trait environments (validates token is configured, not inadvertently transparent).

Dependencies
------------
- None

So that I can quickly understand my performance and improve.

TICKET-M1-GameSessionLifecycle [NEW]
===============================
Ticket: M1 - Game Session Lifecycle / State Machine

User Story
----------
As a developer
I want a shared, testable game session state machine
So that all games handle start, pause, stop, abandon, and completion consistently
and scoring is never written in an invalid state.

Requirements
------------
- Define a GameSession state machine with states:
  - idle, running, paused, completed, abandoned
- Transitions:
  - idle -> running (start)
  - running -> paused (app backgrounded or full-screen exited)
  - paused -> running (returned to full-screen)
  - running -> completed (success condition met)
  - running -> abandoned (timeout, or VO turned off mid-game; see M2-VOStateChangeMidGame)
  - paused -> abandoned (session invalidated while paused)
- Only completed state is eligible to write a best result.
- Session tracks: startTime, elapsed time (accounts for pauses), mistake count.
- Session must be injectable / testable (no direct UIApplication or timer dependencies in the model).

Acceptance Criteria
-------------------
- Starting a session and recording a mistake increments the count correctly.
- Pausing and resuming preserves elapsed time correctly.
- Reaching abandoned state does not trigger a storage write.
- Reaching completed state with a valid result triggers a storage write.

Useful Unit Test
----------------
- Given a session that is paused then abandoned, the resulting state is abandoned
  and no result is passed to storage.
- Given a session that completes, the result passed to storage matches the session's
  elapsed time and mistake count.

Dependencies
------------
- M1 Scoring Model, M1 StorageComponent

Ticket: M1 - Shared Game Result View

User Story
----------
As a user
I want a clear result screen after each game
So that I know my rank and what to work on.

Requirements
------------
- Shared SwiftUI view used by all 3 games (not duplicated per game).
- Displays: rank (text-first; badge/pill is visual decoration only), timeSeconds, mistakes.
- Rank display values: Legendary / Skilled / Novice / Defeated (maps to Perfect/Good/Ok/Failed enum).
- VoiceOver: result must be fully understandable via speech.

- Actions: "Try Again", "Back to Tavern" (was: Play Again / Return to Hub).
- Dynamic Type: all text scales; layout adapts at largest sizes.
- Game-specific result copy: the view accepts an optional game-specific announcement string
  (provided by each game's result presenter) that is announced after the summary.
  Falls back to the shared summary when not provided.
  Example: "The Enchanter bows. A perfect invocation." (Game 1, Legendary)
  See GameRules-MVP.txt for per-game result announcement strings.

Acceptance Criteria
-------------------
- All 3 games route to this view on completion.
- With VoiceOver enabled, rank + metrics are all announced correctly.
- "Try Again" restarts the same game; "Back to Tavern" navigates back.
- Game-specific announcement is announced after the shared summary when provided.

Useful Unit Test
----------------
- Given a Result with rank Perfect, 0 mistakes, 8.5s, the view model produces
  the correct accessibility announcement string (rank first, then metrics).
- Given a game-specific announcement string, the combined announcement includes
  both the shared summary and the game-specific string.

TICKET-M2-VOStateChangeMidGame [COMPLETE]
===============================
Ticket: M2 - VoiceOver Disabled Mid-Gameplay

User Story
----------
As a user
I want the game to handle VoiceOver being turned off during play gracefully
So that the app doesn't end up in an inconsistent or unscored state.

Requirements
------------
- Subscribe to VoiceOver state change notifications during an active game session.
- If VoiceOver transitions OFF while a game session is running or paused:
  - Transition game session to abandoned state.
  - Do not write a result (abandoned sessions are not scored; see GameSessionLifecycle).
  - Navigate to the VO Off interstitial, not to the result screen.
- If VO is re-enabled, user must restart the game; no resume from mid-session.

Acceptance Criteria
-------------------
- With a game running and VO toggled off, the session ends in abandoned state.
- No result is written to storage.
- User lands on the interstitial, not the result screen.

Useful Unit Test
----------------
- Given an active GameSession, injecting a voiceOverDidDisable event causes
  the session to transition to abandoned and calls the abandon handler, not the
  completion handler.

Dependencies
------------
- M2 VoiceOverStateProvider, M1 GameSessionLifecycle

TICKET-M5-Game-EnchantersTrial-FindAndFocus
===============================
Ticket: M5 - Game 1 (The Enchanter's Trial) - Find & Focus
[RENAMED from M5-Game-SimonSays-FindAndFocus to align with GameRules-MVP.txt theme]

User Story
----------
As a user
I want a relic-finding drill that trains VoiceOver focus navigation and activation
So that I can reliably swipe to an element and invoke it with VoiceOver.

VoiceOver Concept Taught
-------------------------
"The screen is linear with VoiceOver — swipe to move, listen to identify, double-tap to act."
This is explicitly taught in L0 before any challenge begins.

Theme / Narrative
-----------------
- The Enchanter's Tower. Magical relics on a shelf. The Enchanter calls a name.
  The player navigates to the named relic and invokes it.
- See GameSpec-FindAndFocus.txt for full narrative and relic pool.

Requirements
------------
- SwiftUI-first implementation.
- 4-level structure (L0 Prologue, L1 First Attempt, L2 Rising Challenge, L3 Timed Trial).

  L0 — Prologue:
  - DM narration card ("The Enchanter's Tower" context).
  - VoiceOver Lesson Card with heading "How VoiceOver Works Here" and explicit
    explanation of the linear navigation paradigm. See GameRules-MVP.txt for exact copy.
  - Gesture reference: swipe right, swipe left, double-tap.
  - "Begin Trial" button (no timer starts until L1).

  L1 — First Attempt:
  - 3 relics: 1 target + 2 decoys. Names are distinct (no close matches).
  - Enchanter's prompt card reads the target name aloud on screen load.
  - No timer. Mistakes allowed but counted.

  L2 — Rising Challenge:
  - 6 relics: includes at least one similar-sounding pair (e.g., Dragon Scale vs Dragon Claw).
  - Soft timer: 45s. VoiceOver announces at 50% and 25% elapsed.

  L3 — Timed Trial:
  - 8 relics, all from the similar-sounding pool.
  - Hard timer: 20s. VoiceOver threshold announcements: 75%, 50%, 25%, 10s, 5s countdown.
  - Thematic timeout: "The candles die. The Enchanter withdraws the relic."
  - Thematic success: "{targetName} invoked in time. The Enchanter is satisfied."

- Relic tokens: see GameSpec-FindAndFocus.txt for full relic pool.
- Prompt format: "The Enchanter calls: {targetName}" (not "Simon says").
- Session managed via GameSessionLifecycle (start, mistake, complete/abandon).
- Mistakes: wrong relic activation (+1), time-based mistake buckets (bucket: 10s).
- Optional hint button: "The Enchanter whispers: the target is {name}." No scoring penalty.
- On completion: route to SharedGameResultScreen with computed rank + game-specific result copy.
  Game-specific copy: "The Enchanter bows. A perfect invocation." (Legendary), etc.
- Persist best result via StorageComponent.
- GameSessionCoordinator monitors VoiceOver state; VO disabled mid-session → abandon.

Acceptance Criteria
-------------------
- L0 lesson card is shown before any challenge. Player cannot bypass it.
- With VoiceOver ON, all 4 levels are completable by swipe navigation alone.
- Wrong relic activation increments the mistake count.
- Timeout transitions session to abandoned (not completed); no result written.
- Timer announces at all required thresholds (see GameRules-MVP.txt timer spec).
- Thematic timeout/success strings are announced by VoiceOver.
- Result persists; best result updates when improved.

Useful Unit Test
----------------
- Given (timeSeconds: 9, mistakes: 0), rank evaluates to Legendary for this game's thresholds.
- Given (timeSeconds: 46, mistakes: 0), rank evaluates to Defeated (timeout exceeded).

Dependencies
------------
- M0, M1 (Scoring Model, Storage, GameSessionLifecycle, SharedGameResultScreen), M2 VO gating
- Design track: enchanter relic assets must land before this ticket opens.

TICKET-M6-Game-RoguesGauntlet-Activate
===============================
Ticket: M6 - Game 2 (The Rogue's Gauntlet) - Activate / Double-Tap
[RENAMED and REVISED from M6-Game-BombDefusal-Activate to align with GameRules-MVP.txt theme]

User Story
----------
As a user
I want a seal-severing challenge that explicitly teaches double-tap activation in VoiceOver
So that I understand that single tap examines, and double-tap invokes — and I can use this reliably.

VoiceOver Concept Taught
-------------------------
"With VoiceOver on, tapping once reads an element — it does NOT activate it. Double-tap to act."
This is the single most common VoiceOver confusion. L0 must make this explicit.

Theme / Narrative
-----------------
- The Trap Room. Magical seals on a locked door. One seal unlocks the door; others spring traps.
- "Touch to sense. Double-tap to sever."
- See GameSpec-ActivateDoubleTap.txt for full narrative and seal pool.

Requirements
------------
- SwiftUI-first implementation.
- 4-level structure (L0 Prologue, L1 First Attempt, L2 Rising Challenge, L3 Timed Trial).

  L0 — Prologue:
  - DM narration card ("The Trap Room" context).
  - VoiceOver Lesson Card with heading "The Rogue's Creed" and explicit explanation:
    "Tapping once reads the element — it does not activate it. Double-tap to activate."
    Contrast clearly: "This is different from normal iOS."
  - Gesture reference: one tap (examine/focus only), double-tap (sever/activate).
  - "Begin Trial" button.

  L1 — First Attempt (confidence builder):
  - 1 seal only (Seal of Passage). No trap seals.
  - Purpose: isolate the double-tap mechanic with no ambiguity about which seal to pick.
  - "Touch it to hear it speak. Double-tap to sever it."

  L2 — Rising Challenge:
  - 4 seals: 1 passage seal + 3 trap seals with distinct descriptive names.
  - Wrong activation = trap springs = misstep.
  - Soft timer: 40s. VoiceOver announces at 50% and 25% elapsed.

  L3 — Timed Trial:
  - 6 seals: 1 passage seal + 5 trap seals.
  - Hard timer: 20s. VoiceOver threshold announcements: 75%, 50%, 25%, 10s, 5s countdown.
  - Thematic timeout: "The trap room sealed. You were caught."
  - Thematic success: "Seal severed. The door opens just in time."

- Seal names: see GameSpec-ActivateDoubleTap.txt for full seal pool (passage + trap seals).
- Prompt format: "Sever the seal: {sealName}" (not "Disarm: cut the <wire>").
- Elements are "seals" (not wires). Distinct descriptive labels; no color-only differentiation.
- Session managed via GameSessionLifecycle (start, mistake, complete/abandon).
- Mistakes: wrong seal activation (+1), time-based mistake buckets (bucket: 8s).
- Optional hint: "The Enchanter reminds you: double-tap to sever." No scoring penalty.
- On completion: route to SharedGameResultScreen with computed rank + game-specific result copy.
  Game-specific copy: "Flawless. No trap touched you." (Legendary), etc.
- Persist best result via StorageComponent.
- GameSessionCoordinator monitors VoiceOver state; VO disabled mid-session → abandon.

Acceptance Criteria
-------------------
- L0 lesson card explicitly teaches the touch ≠ activate paradigm.
- L1 has exactly one seal; no wrong activation possible.
- With VoiceOver ON, all levels are completable.
- Trap seal activation increments mistakes; passage seal activation succeeds.
- Timeout transitions to abandoned; no result written.
- Timer announces at all required thresholds.
- Result persists; best score updates correctly.

Useful Unit Test
----------------
- Given (timeSeconds: 7, mistakes: 0), rank evaluates to Legendary for this game's thresholds.
- Given two results with equal rank, the result with fewer mistakes is selected as best.

Dependencies
------------
- M0, M1 (Scoring Model, Storage, GameSessionLifecycle, SharedGameResultScreen), M2 VO gating
- Can be built in parallel with M5 once shared infrastructure (M0/M1/M2) is complete.
- Design track: rogue seal assets must land before this ticket opens.

TICKET-M7-Game-DungeonDescent-ScrollHunt
===============================
Ticket: M7 - Game 3 (The Dungeon Descent) - Scroll Hunt
[RENAMED from M7-Game-DungeonCrawl-ScrollHunt to align with GameRules-MVP.txt theme]

User Story
----------
As a user
I want a dungeon-descent challenge that trains three-finger scrolling with VoiceOver
So that I can reliably scroll to reveal and reach offscreen content.

VoiceOver Concept Taught
-------------------------
"Single-finger swipe navigates elements — it does NOT scroll the page. Use three fingers to scroll."
This is explicitly taught in L0, with a practice scroll area before the first challenge.

Theme / Narrative
-----------------
- The Dungeon Descent. Vertical dungeon chambers. The relic lies below the visible screen.
  Three-finger scroll to descend. Each room read by VoiceOver as focus moves to it.
- See GameSpec-ScrollHunt.txt for full room list and narrative.

Requirements
------------
- SwiftUI-first implementation using the approach validated in S1 Spike.
- 4-level structure (L0 Prologue, L1 First Attempt, L2 Rising Challenge, L3 Timed Trial).

  L0 — Prologue:
  - DM narration card ("The Dungeon Descent" context).
  - VoiceOver Lesson Card with heading "Descending the Dungeon" and explicit explanation:
    "Swiping moves between items — not the page. Use three fingers to scroll."
  - Gesture reference: 1-finger swipe (items), 3-finger swipe up (scroll down), 3-finger swipe down (scroll up).
  - Practice scroll area: labeled scrollable zone where player practices 3-finger scroll
    before attempting L1. This zone must be present and accessible before "Begin Descent" appears.
  - "Begin Descent" button.

  L1 — First Attempt (no timer):
  - 4 rooms: 2 visible, 2 below fold. Target: Guard Room (depth 2).
  - Single scroll + activation to succeed.
  - Non-interactive rooms give "Nothing useful here. Keep descending." on double-tap.

  L2 — Rising Challenge (soft timer: 60s):
  - 8 rooms: 3 visible, 5 below fold. Target: Relic Vault (near bottom).
  - Non-interactive rooms give feedback on double-tap.
  - VoiceOver announces at 50% and 25% elapsed.

  L3 — Timed Trial (hard timer: 45s):
  - 12 rooms: 3 visible, 9 below fold. Target: Ancient Vault (depth 10+).
  - Hard timer. VoiceOver threshold announcements: 75%, 50%, 25%, 10s, 5s countdown.
  - Thematic timeout: "The gate fell. The relic is sealed below. Trial failed."
  - Thematic success: "Ancient Vault reached. The relic is yours. Trial passed."

- Room list: see GameSpec-ScrollHunt.txt for full room pool with accessibility labels.
- Non-interactive rooms: no button trait; double-tap gives "Nothing useful here" feedback.
- Target rooms: button trait; accessibilityHint "Double-tap to claim this room."
- No "Jump to target" UI. Success requires scroll progress AND target activation.
- We do not detect the exact gesture; we validate scroll outcome (progress / visibility).
- Session managed via GameSessionLifecycle.
- Mistakes: non-target activation (+1), time-based mistake buckets (bucket: 15s).
  Optional wrong-direction scroll penalty only if S1 Spike confirms reliable detection.
- Optional hint button: "Use three fingers to scroll downward." No scoring penalty.
- On completion: route to SharedGameResultScreen with computed rank + game-specific result copy.
  Game-specific copy: "Legendary descent. No misstep. The dungeon bows." (Legendary), etc.
- Persist best result via StorageComponent.
- GameSessionCoordinator monitors VoiceOver state; VO disabled mid-session → abandon.

Acceptance Criteria
-------------------
- L0 practice scroll area is present and usable before L1 begins.
- L0 lesson card explicitly teaches the 3-finger scroll paradigm.
- User must scroll to reach the target; target is not activatable until reachable.
- Non-target room double-tap gives feedback but does not record success.
- Anti-cheat: no affordance allows bypassing scroll.
- Timer announces at all required thresholds.
- Result persists; best score updates correctly.

  "targetIsReachable" becomes true only at the expected threshold.
