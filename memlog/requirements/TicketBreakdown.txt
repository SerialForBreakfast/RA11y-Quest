So that I can reach the hub and return from any screen without dead ends.

TICKET-M0-DesignTokens [NEW]
===============================
Ticket: M0 - Shared Design Token System

User Story
----------
As a developer
I want a single source for typography, spacing, and color constants
So that all screens are visually consistent and can adopt system accessibility overrides correctly.

Requirements
------------
- Define design tokens covering:
  - Typography: font styles aligned to Dynamic Type text styles (title, headline, body, caption).
  - Spacing: a small step scale (e.g., 4, 8, 12, 16, 24, 32pt).
  - Corner radius: consistent values (e.g., card, button, badge).
  - Colors: semantic color set (background, surface, primary, secondary, destructive) using adaptive
    Color assets compatible with Increase Contrast and Dark Mode.
- Tokens must be defined in a way that resolves correctly under system accessibility overrides
  (Increase Contrast, Reduce Transparency, Dark Mode).
- No raw numeric literals for spacing, radius, or color in UI code; token references only.

Acceptance Criteria
-------------------
- Token definitions exist and are consumable from SwiftUI views.
- Changing a token propagates correctly to all uses.
- UI remains legible under Increase Contrast and Dark Mode.

Useful Unit Test
----------------
- Color token for primary surface returns a non-zero opacity value in both Light and Dark
  trait environments (validates token is configured, not inadvertently transparent).

Dependencies
------------
- None

So that I can quickly understand my performance and improve.

TICKET-M1-GameSessionLifecycle [NEW]
===============================
Ticket: M1 - Game Session Lifecycle / State Machine

User Story
----------
As a developer
I want a shared, testable game session state machine
So that all games handle start, pause, stop, abandon, and completion consistently
and scoring is never written in an invalid state.

Requirements
------------
- Define a GameSession state machine with states:
  - idle, running, paused, completed, abandoned
- Transitions:
  - idle -> running (start)
  - running -> paused (app backgrounded or full-screen exited)
  - paused -> running (returned to full-screen)
  - running -> completed (success condition met)
  - running -> abandoned (timeout, or VO turned off mid-game; see M2-VOStateChangeMidGame)
  - paused -> abandoned (session invalidated while paused)
- Only completed state is eligible to write a best result.
- Session tracks: startTime, elapsed time (accounts for pauses), mistake count.
- Session must be injectable / testable (no direct UIApplication or timer dependencies in the model).

Acceptance Criteria
-------------------
- Starting a session and recording a mistake increments the count correctly.
- Pausing and resuming preserves elapsed time correctly.
- Reaching abandoned state does not trigger a storage write.
- Reaching completed state with a valid result triggers a storage write.

Useful Unit Test
----------------
- Given a session that is paused then abandoned, the resulting state is abandoned
  and no result is passed to storage.
- Given a session that completes, the result passed to storage matches the session's
  elapsed time and mistake count.

Dependencies
------------
- M1 Scoring Model, M1 StorageComponent

TICKET-M2-VOStateChangeMidGame [NEW]
===============================
Ticket: M2 - VoiceOver Disabled Mid-Gameplay

User Story
----------
As a user
I want the game to handle VoiceOver being turned off during play gracefully
So that the app doesn't end up in an inconsistent or unscored state.

Requirements
------------
- Subscribe to VoiceOver state change notifications during an active game session.
- If VoiceOver transitions OFF while a game session is running or paused:
  - Transition game session to abandoned state.
  - Do not write a result (abandoned sessions are not scored; see GameSessionLifecycle).
  - Navigate to the VO Off interstitial, not to the result screen.
- If VO is re-enabled, user must restart the game; no resume from mid-session.

Acceptance Criteria
-------------------
- With a game running and VO toggled off, the session ends in abandoned state.
- No result is written to storage.
- User lands on the interstitial, not the result screen.

Useful Unit Test
----------------
- Given an active GameSession, injecting a voiceOverDidDisable event causes
  the session to transition to abandoned and calls the abandon handler, not the
  completion handler.

Dependencies
------------
- M2 VoiceOverStateProvider, M1 GameSessionLifecycle

TICKET-M5-Game-SimonSays-FindAndFocus
===============================
Ticket: M5 - Game 1 (Simon Says) - Find & Focus

User Story
----------
As a user
I want a Simon Says-style drill that trains focus navigation and correct activation
So that I can reliably select the intended element with VoiceOver.

Theme / Narrative
-----------------
- Simon Says training drill inside the Training Academy.

Requirements
------------
- SwiftUI-first implementation.
- Present a small set of controls: 1 target + multiple decoys.
- Prompt: "Simon says: activate <target>."
- Success: target control's activation handler is invoked.
- Session managed via GameSessionLifecycle (start, mistake, complete/abandon).
- Mistakes: wrong activation of a decoy, time-based mistake buckets (per GameSpec-FindAndFocus).
- Optional hint button does not affect scoring.
- On completion: route to SharedGameResultView with computed rank + metrics.
- Persist best result via StorageComponent.

Acceptance Criteria
-------------------
- With VoiceOver ON, the game can be completed reliably.
- Wrong activation increments the mistake count in the session.
- Timeout transitions session to abandoned (not completed).
- Result persists and best result updates when improved.

Useful Unit Test
----------------
- Given (timeSeconds: 9, mistakes: 0), rank evaluates to Perfect for this game's thresholds.
- Given (timeSeconds: 46, mistakes: 0), rank evaluates to Failed (timeout exceeded).

Dependencies
------------
- M0, M1 (Scoring Model, Storage, GameSessionLifecycle, SharedGameResultScreen), M2 VO gating

TICKET-S1-Spike-ScrollObservability [PROMOTED]
===============================
Ticket: S1 - Spike: Scroll Observability in SwiftUI

GATE: This spike must close (findings documented) before TICKET-M7-DungeonCrawl-ScrollHunt opens.

User Story
----------
As a developer
I want a proven approach to observe scroll progress in SwiftUI
So that Scroll Hunt (M7) can be implemented reliably on iOS 18/26 on iPhone and iPad
without guessing at implementation strategy.

Requirements
------------
- Build a minimal prototype that:
  - Observes scroll progress using SwiftUI scroll APIs
    (primary: onScrollGeometryChange + ScrollGeometry; see Spike-ScrollObservability-SwiftUI.txt).
  - Derives a stable, equatable progress signal suitable for game use.
  - Flips a "target revealed" boolean when progress reaches the intended threshold.
- Document findings: which derived values were stable, update frequency, any OS/device differences,
  recommended strategy for M7.
- Prototype must work on iPhone and iPad, portrait and landscape full-screen.
- Prototype is throwaway; it does not ship.

Acceptance Criteria
-------------------
- Scrolling causes the derived progress value to update.
- "Target revealed" flips only at the intended threshold.
- Findings document exists and includes a clear recommended approach for M7.
- Prototype verified on both iPhone and iPad, portrait + landscape.

Useful Unit Test
----------------
- Pure function: mapping from raw scroll signal(s) to DerivedProgress is monotonic
  and reaches "targetVisible = true" at the configured threshold.

Dependencies
------------
- M0 (can start early; does not need M1/M2)

- Result persists; best score updates correctly.

Useful Unit Test
----------------
- Rank evaluation for Dungeon Crawl uses the correct per-game thresholds
  (e.g., Perfect: 0 mistakes AND time <= 15s).
- Scroll progress mapping function: given a mocked scroll offset sequence,

Dependencies

TICKET-M8-Accessibility-Audit-Polish
===============================
Ticket: M8 - Accessibility Audit + MVP Polish

User Story
----------
As a user
I want the app to be a best-practice accessibility example
So that it is comfortable, readable, and reliable across a wide range of needs.

Requirements
------------
- Verify compatibility with:
  - Dynamic Type (all sizes, including largest accessibility sizes)
  - Increase Contrast
  - Reduce Transparency
  - Reduce Motion (no motion-only cues for critical information)
- Verify VoiceOver quality across all screens:
  - Deterministic reading order
  - Correct labels and hints on all interactive controls
  - Decorative imagery marked as decorative
  - Rank + metrics announced correctly via speech (from SharedGameResultView)
- Verify iPhone + iPad, portrait and landscape in full-screen.
- Verify game session stops cleanly on full-screen exit (via GameSessionLifecycle abandoned state).
- Copy pass: instructional copy is clear, concise, consistent.
- Visual polish pass: native look, consistent use of design tokens.

Acceptance Criteria
-------------------
- Smoke test passes on iPhone + iPad, portrait and landscape.
- No critical information conveyed only via color on any screen.
- Leaving full-screen stops gameplay and does not write a result.
- No blocking accessibility defects in the smoke test path.

Useful Unit Test
----------------
- Given a running GameSession, a "fullScreenExited" event causes the session to transition
  to abandoned state (not completed), and the storage write is not invoked.

Dependencies
------------
